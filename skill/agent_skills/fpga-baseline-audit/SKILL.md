# FPGA 构建与部署来源审计

## 工作流程
1. 先确认用户指定的权威工程、目标板卡和只读边界；目录名称或文件时间不能证明版本。
2. 读最新任务日志、工程README；记录代码、封装IP、实际综合源、生成副本与部署位置。通过 Tcl source清单/构建日志确认实际来源，不仅搜索同名文件。
3. 比较源哈希；说明有意的差异，不擅自覆盖封装源或生成文件。引用 PYNQ工具 source_identity.py 可做只读字节比较，但它不能发现Vivado实际选择了哪个文件。
4. 核对同次构建的bit/hwh、器件、地址、IP身份和协议VERSION；哈希相同仅证明文件相同，不证明板上加载。
5. 需要变更构建时先列范围和回退；实际重建走Tcl，不手改xpr。保留多串口、XDC和用户改动。
6. 部署前给出安全停机步骤；只有明确授权才下载。实际读取VERSION及IP映射后才标注BOARD验证。
7. 报告每层证据，不把综合通过当成硬件通过。

## 何时用 / 何时不用

**用**：改过 IP 之后位流行为不对；`bit` 和 `hwh` 不是同一次构建产出；多个目录里各有一份同名源文件；怀疑综合读的不是你以为的那份 `.v`。

**不用**：只有一次干净构建、源目录唯一时，这套审计只是重复劳动。先跑一次 `report_utilization` 确认数字对得上更快。

## 使用与输出

给本流程：权威输入（工程路径、构建日志原文，不是摘要）、异常现象原文、只读或写入授权。输出使用 [报告模板](assets/report.md)。缺少用户独占事实时一次询问最阻塞的问题；不要把历史工程参数迁到新板。

一句话就能启动：

> 我改了 `fpd_settle_fit.v` 之后 WNS 不升反降。请只读审查：Vivado 实际综合的是哪一份源文件，`build_provenance.json` 里的哈希和当前磁盘是否一致，以及这次 `bit` 与 `hwh` 是不是同一次构建。不要重建、不要下载。
